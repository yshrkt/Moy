# Moy：macOS 26向けlaunchdジョブ管理アプリ

## 1. 技術構成とモジュール

Apple Silicon搭載MacのmacOS 26以降を対象に、Xcode 27・Swift 6.4・SwiftUI・NanoReduxで実装する。Swiftの言語モードはSwift 6とする。Tuistのプロジェクト共通設定で`ARCHS = arm64`を指定し、アプリ・同梱CLI・共通モジュールのDebug／Release／ArchiveをApple Silicon向けに限定する。Moyで登録したユーザー単位のLaunchAgentを管理し、メニューバーから状態確認・操作、管理ウィンドウから登録・編集を行う。

MiroCalの責務分離・命名規則・Tuist設定を参考に、以下の3モジュールに分ける。

```text
Sources/
  MoyApp/
    Core/<機能名>/       # Action・State・Reducer・Dependencies
    Views/              # SwiftUIの画面
    MoyApp.swift        # アプリのエントリーポイント
  MoyCLI/               # 引数解析・表示・エントリーポイント
  MoyKit/
    Domain/
      Models/
      Repositories/
      UseCases/
    Platform/
      Repositories/
      UseCases/

Resources/
  MoyApp/
    ja.lproj/
    en.lproj/

Tests/
  MoyAppTests/
  MoyCLITests/
  MoyKitTests/
```

- 依存関係は`MoyApp → MoyKit`、`MoyCLI → MoyKit`とする。
- NanoReduxはMoyAppのみで使用し、確認済みの`0.1.2`をSPM経由で導入する。
- Domainにはモデルとprotocol、PlatformにはJSON保存・launchd操作などの具体実装を置く。
- 作成時の入力は`ServiceDraft`、保存済みの完全な定義は`ServiceDefinition`で表現する。
- RepositoryとUseCaseの公開メソッドは`async throws`とし、NanoReduxのEffectから`await`で呼び出す。
- JSON保存とlaunchd操作の実装にはactorを使用し、同一プロセス内の操作を直列化する。
- Actionは`enableService`などの動詞＋対象、UseCaseは`...UseCase`、既定実装は`Default...UseCase`とする。
- 機能ごとにAction／State／Reducer／Dependenciesを別ファイルにする。
- 製品名は`Moy.app`と`moy`。CLIをアプリに同梱する。
- mise＋Tuistで依存解決・プロジェクト生成を管理し、`generate`、`build`、`test`、`format`、`lint`を用意する。フォーマット設定もMiroCalを基準にする。
- アプリは`LSUIElement`を有効にし、ユーザーのLaunchAgentsを操作するためApp Sandboxを無効にする。

## 2. サービス定義とJSON保存

### 設定項目

初期版で扱うplist項目は次の9つとする。

| 項目 | 扱い |
|---|---|
| `Label` | 固定prefixとIdentifierから生成し、直接編集させない |
| `ProgramArguments` | 編集UIでは実行ファイルと順序付き引数を分け、詳細画面ではコピー可能なコマンド、plistでは配列にする |
| `WorkingDirectory` | 任意指定。フォルダ選択に対応 |
| `EnvironmentVariables` | 任意の文字列キー／値を一覧で編集 |
| `RunAtLoad` | Boolean。初期値OFF |
| `KeepAlive` | 初期版はBooleanのみ。初期値OFF |
| `ThrottleInterval` | 任意の秒数。未指定ならキーを省略する |
| `StandardOutPath` | 空欄時はMoyの既定パスを使用。新規作成時はプレースホルダーで表示し、変更可能 |
| `StandardErrorPath` | 空欄時はMoyの既定パスを使用。新規作成時はプレースホルダーで表示し、変更可能 |

実行ファイルは絶対パスで指定し、暗黙のシェル実行・シェル初期化は行わない。GUI・CLI共通の保存処理で存在と実行可否を確認する。コマンド名だけの入力・相対パス・存在しないパス・リンク切れは「実行ファイルが見つかりません。絶対パスで指定し、パスとファイル名を確認してください。」という共通エラーにする。ディレクトリや実行権限のないファイルは別の実行不可エラーにする。既存定義の読み込み時は存在・実行権限を検証せず、実行ファイルが削除された後も定義を開いて修正・削除できるようにする。RunAtLoadがLaunchAgentの読み込み時にサービスを起動する設定であること、KeepAliveが読み込み時の起動も伴うこと、ThrottleIntervalは短時間での再起動の繰り返しを抑えるための最小起動間隔（秒）であり、未指定時はOSの既定値を使い、定期実行の間隔ではないことをUIで説明する。

### Identifier、Label、メタデータ

サービス作成時にユーザーがIdentifierを指定し、Labelは以下の形式で生成する。

```text
Identifier: api-server
Label:      com.sputnik-apps.moy.api-server
```

- Identifierは1〜64文字のASCII小文字英数字・ハイフン・アンダースコアとし、先頭・末尾は英数字に限定する。
- IdentifierはMoy内で一意かつ作成後は変更不可とする。Swiftの`Identifiable.id`もIdentifierを返す。
- 共通層で既存定義・plist・launchdとの重複を検査し、衝突時は登録エラーとする。検査不能時も登録エラーとする。
- 重複検査から保存までをロック内で行い、GUI／CLIの同時登録に対応する。
- Labelは`com.sputnik-apps.moy.<Identifier>`として算出し、JSONには保存しない。
- 無効化・再有効化や設定変更でもIdentifierとLabelを維持する。
- plist名は`<Label>.plist`とする。
- 表示名とdescriptionは任意の編集可能なメタデータとして保存し、plistには含めない。
- 一覧は表示名を優先し、未設定ならIdentifierを表示する。詳細画面ではIdentifierとLabelを確認・コピーできる。
- メタデータだけの変更では再読み込み・再実行を行わない。
- 既定のログ保存先にはLabelを使い、表示名変更で変わらないようにする。

### 永続化

全サービスを次のJSONファイルにまとめる。

```text
~/Library/Application Support/Moy/
  services.json
  services.lock
```

JSONは`schemaVersion`とサービス一覧を持ち、各サービスに必須の`kind`・表示名・description・9項目のlaunchd設定を保存する。現在の`kind`は`launchAgent`のみを扱い、GUI／CLIからの新規登録にも保存する。`kind`はplistには含めない。

- JSONを編集用データの正本とし、有効なサービスのplistだけをユーザーのLaunchAgentsに配置する。
- 無効化してもJSONの定義は残す。
- 有効／無効はplistの有無から判定し、launchdの読み込み状態と照合する。PIDなどの実行状態は永続化しない。
- App／CLI間はactorを共有できないため、共通の`flock`でJSONの読み込み・変更・原子的な保存を直列化する。
- ファイルロックを保持したまま`await`せず、ロック内は同期的なJSON操作だけに限定する。
- 古い編集内容による上書きを防ぎ、競合時は再取得を促す。
- JSON破損や未対応バージョンを空データとして扱わず、上書きを防ぐ。
- 設定ディレクトリとファイルは所有ユーザーだけがアクセスできる権限にする。

### 個別サービスのJSONインポート・エクスポートと複製

以下は追加機能の合意済み仕様を記録するものであり、実装は別途依頼を受けて開始する。

先行対応のGUIの「保存して有効化」の削除・保存Actionの簡素化とIdentifierの入力中検証は対応済み。MoyKitとCLIの個別JSONインポート・エクスポートも対応済み。GUIの個別JSONインポート・エクスポートも対応済み。複製は未実装。

#### 合意済みの方針

- 実装順序は、まずGUIのIdentifier入力中検証と新規作成の保存操作の簡素化に対応し、その後にインポート・エクスポート・複製へ進む。
- JSONのインポート・エクスポートは個別サービスを対象とし、GUIとCLIの両方で対応する。
- 個別ファイルはschemaVersionを1とし、トップレベルにschemaVersionと1件のserviceを持つ。Identifier、kind、programArguments、environmentVariables、runAtLoad、keepAlive、standardOutPath、standardErrorPathは必須。displayName、description、workingDirectory、throttleIntervalは任意とする。エクスポートでは設定済みの任意項目も含める。未対応バージョン・kind・未知のキーは形式エラーとする。environmentVariables内のユーザー指定の名前は未知のキーの検査対象にしない。
- 任意項目はSwiftのCodableの合成実装に準拠し、エクスポートではnilのキーを省略する。インポートではキー欠落・nullを未指定として扱い、値がある場合は型を検証する。必須のログ保存先の空文字ルールとは区別する。
- サービスの状態以外の設定項目をすべて対象とする。Identifier、kind、表示名、description、ProgramArguments、WorkingDirectory、EnvironmentVariables、RunAtLoad、KeepAlive、ThrottleInterval、StandardOutPath、StandardErrorPathを扱う。ログ保存先は「Moyの既定パスを使用する」設定も含めて入出力する。
- ログ保存先の引き継ぎはインポート・複製で統一する。既定パスは未指定として引き継ぎ、保存時に保存先環境と新規登録するIdentifierから既定パスを生成する。独自パスは指定値を保持する。標準出力・標準エラーそれぞれにこのルールを適用する。
- 個別サービスJSONのstandardOutPath／standardErrorPathでは、空文字（`""`）を「Moyの既定パスを使用する」と定義する。エクスポートでは両キーを文字列として含め、既定パスは空文字、独自パスは指定値を出力する。GUIでは既定パスのログ入力欄を空欄とし、Identifierの変更に合わせて既定パスのプレースホルダーを更新する。この表現は個別ファイル用であり、内部保存用services.jsonの形式は変更しない。
- 個別サービスJSONのログ保存先は両キーを必須の文字列とし、null・キー欠落・文字列以外は形式エラーとする。空白だけの文字列は空文字へ変換せず、パスの入力エラーとする。
- Labelは従来どおりIdentifierから生成する。有効／無効、PID、前回の終了結果などの状態やログ内容は設定の入出力に含めない。
- GUIのサービス一覧の「＋」は「新規」「インポート…」のメニューにする。「新規」は従来の新規作成を開き、「インポート…」はJSONファイルを選択する。
- GUIのインポートと複製は、設定を引き継いだ新規作成の編集画面を開き、確認・修正してから保存する共通の流れにする。
- Identifierの文字種・長さ・先頭末尾の形式・重複は、新規作成・インポート・複製で共通に検証し、Label（Identifier）の入力欄の下に理由を赤字で表示する。形式は既存の1〜64文字のASCII小文字英数字・ハイフン・アンダースコア、先頭末尾は英数字という規則を維持する。重複は「重複しています。」に相当する日英メッセージとする。入力は自動補正せず、修正後に表示を更新する。
- Identifierが空欄の場合は、初期表示も含め「Identifierを入力してください。」に相当する日英メッセージを表示する。入力経験やフォーカスによるエラーの表示制御は行わない。入力欄の下にcaptionの2行分のメッセージ領域を常に確保し、正常時・検証待ち中も同じ高さを維持する。エラーがない場合は空白とし、空白の領域はアクセシビリティの読み上げ対象から除く。入力値はAction経由で即時にStateへ反映し、ReducerがNanoReduxの300msのdebounceで検証Effectを起動する。検証結果はActionで受け取りStateに保持する。Stateのcomputed propertyで形式や重複の検証を実行しない。文字種・先頭末尾はMoyKitのValidatorでRegex、長さはcountで検証する。入力中の重複検査はGUIが保持している既存サービス一覧のIdentifierとの照合だけとし、JSONの再読み取り・ファイルロック取得・plist検査・launchctlの照合は行わない。検証待ちの間は保存を無効にし、専用の確認中表示は設けない。新しい入力の検証待ち中も直前の検証結果とメッセージを維持し、結果を受け取ったときだけ更新する。検証開始によるメッセージの消去・再表示を行わない。検証リクエストIDは設けず、検証対象の入力値をStateに保持して検証待ちを表す。結果の編集セッションIDと入力値を現在の値と照合し、別セッションや異なる入力の結果は破棄する。同じ入力値に戻った場合は一致する結果を受け入れる。Identifierが空欄・不正・一覧内の既存Identifierと重複する場合も保存操作を無効にする。編集中にサービス一覧が更新された場合も重複判定を更新する。既存サービスの編集ではIdentifierが変更不可のため、自分自身との重複エラーを出さない。
- 保存時は既存の共通登録処理で定義・plist・launchdとの衝突を厳密に検査する。GUI／CLIによる同時変更など、入力中の簡易検査で検出できなかった重複や検査失敗は、保存エラーとして既存の編集画面のエラー表示で伝える。
- GUIインポートでIdentifierが重複していても編集画面を開き、入力欄の下にエラーを表示する。Identifierを変更して保存できるようにする。入力中の検証は保存時の共通層による再検証を代替しない。
- GUIの複製は詳細右上に「複製」を追加し、Identifierを空欄にして編集画面を開く。表示名・descriptionは引き継ぐ。
- GUIの新規登録・インポート・複製の保存操作は「保存」のみとし、「保存して有効化」は削除する。保存では定義のJSONだけを保存し、plistの作成・launchdへの登録・起動は行わない。成功時は編集画面を閉じ、保存したサービスを選択して詳細画面を表示する。有効化は詳細画面の操作から行う。CLIのadd・インポート・複製は通常は保存のみ、--enable指定時に保存して有効化する。元サービスの有効状態は引き継がない。
- サービス詳細右上の編集・削除と並ぶ操作として「エクスポート…」を追加する。
- Identifierの重複は登録エラーとし、既存サービスを上書きしない。CLIのインポートでは、重複時に英語のエラーを表示し、非ゼロの終了コードを返す。
- CLIの複製は`moy copy <source-identifier> <destination-identifier>`とする。例：`moy copy api-server new-api-server`。コピー元と新規登録するIdentifierを順番に位置引数で指定する。コピー先のIdentifierが重複する場合は英語のエラーを表示し、非ゼロの終了コードを返す。
- CLIのインポートは`moy import <file> [--enable]`、エクスポートは`moy export <identifier> --output <file>`とし、初期対応はファイルの入出力に限定する。既存のshow --jsonは維持し、個別ファイルのインポートに使用する形式はexportで出力する。
- GUIのエクスポートは保存ダイアログで既存ファイルへの上書きを確認する。
- GUIのファイル選択・保存先選択はJSONファイルを対象とする。選択・読み込み・書き込み中は新規作成・編集・別の入出力を開始できない。インポートはreadServiceの結果を新規作成モードの編集画面へ展開し、初期のIdentifier重複はその場で検証する。JSON形式エラーは日英の説明に詳細を併記し、編集画面を開かず管理画面で表示する。
- GUIエクスポートの既定ファイル名は`<identifier>.json`とする。
- CLIエクスポートは、ユーザーが指定した出力ファイルを確認なし・--forceなしで上書きする。入力検証やJSON生成に失敗した時点では既存ファイルを変更せず、保存は原子的に行う。
- 存在しない親ディレクトリ・ディレクトリへの出力・書き込み権限不足など、保存できない出力先は通常のファイル保存エラーとして扱う。特殊な出力先に専用の確認画面や復旧フローは追加しない。
- GUIのインポート・複製の保存成功は詳細画面への遷移で示し、エクスポート成功時は追加通知を表示しない。ファイル選択・保存先選択・編集のキャンセルは通知しない。失敗時は既存のエラー表示を使用する。CLIは成功メッセージと終了コード、失敗時は英語のエラーと非ゼロの終了コードで伝える。
- 現状の内部保存は既定ログパスも絶対パスで保持するため、エクスポート・複製時は元のIdentifierとMoyPathsから求めた既定パスとの一致で判定し、一致したものを空文字へ変換する。
- JSONの構造・型・バージョンなどの形式検証と、登録時の入力・環境検証を分ける。形式不正は編集画面を開く前にエラーとする。GUIではIdentifierの入力エラー・重複や実行ファイルの不在などを編集画面で修正して保存できる。CLIでは既存のaddと同じ保存時検証を行い、実行ファイルが見つからない・実行できない場合は英語のエラーを表示し、保存せず非ゼロの終了コードを返す。
- JSON形式の処理・入力検証・登録はMoyKitに集約し、GUI／CLIで共用する。

- 独自ログパスの共有に関するGUIの説明の表示方法。
- 処理中の重複操作の防止、シンボリックリンクへの保存などのファイル操作の詳細は、上記の通常保存・エラー処理の範囲で整理する。

#### 個別JSONの実装と例

- `ServiceJSONDocument`は内部保存とは別のバージョン付き形式とし、未知のトップレベルキーとservice内のキーを拒否する。環境変数の名前は自由な辞書キーとして扱う。
- `ServiceDocumentRepository`／`JSONServiceDocumentRepository`がファイルを読み書きし、`ServiceTransferUseCase`／`DefaultServiceTransferUseCase`が既存の登録処理との接続と既定ログパスの変換を担当する。
- readServiceはファイルの形式を検証してServiceDraftを返し、登録・実行ファイルの存在確認は行わない。importServiceはそのDraftを既存のcreateへ渡して入力・実行ファイル・重複を検証する。exportServiceは保存済み定義を取得し、実行ファイルが削除されていても出力できる。
- 出力はUTF-8、整形済み、キーをソートしたJSONとし、末尾に改行を付ける。ファイル選択や標準入力・標準出力の入出力はCLIの初期対応に含めない。CLIのファイルパスには相対パスも使用できる。
- JSONの形式エラーはServiceJSONError、ファイル操作・登録エラーは既存のMoyErrorで返す。--enableでの有効化失敗は既存のcreateと同じ後片付け・エラー処理を使用する。

任意項目を省略し、既定のログ保存先を使用する例：

```json
{
  "schemaVersion": 1,
  "service": {
    "environmentVariables": {},
    "identifier": "example-job",
    "keepAlive": false,
    "kind": "launchAgent",
    "programArguments": ["/usr/bin/sleep", "60"],
    "runAtLoad": false,
    "standardErrorPath": "",
    "standardOutPath": ""
  }
}
```

### LaunchDaemon対応に向けた保存形式の方針

- 将来LaunchDaemonに対応しても、編集用の定義は共通の`services.json`内の`services`配列で管理する。Agent／Daemon別のファイルや配列には分割しない。
- IdentifierはLaunchAgent／LaunchDaemonを通して一意とし、既存のLabel生成規則を維持する。
- 種別は各サービスの`kind`で表し、機械可読な値を`launchAgent`／`launchDaemon`とする。
- Daemonの操作対応に先行して、必須項目`kind`を追加する。現在は`launchAgent`のみを受け付け、`launchDaemon`はDaemon対応時に追加する。開発中のため`kind`がない定義の互換読み込み・自動移行は用意せず、既存の開発用JSONには直接`launchAgent`を追加する。`schemaVersion`は1を維持する。欠落・未対応の`kind`は読み込みエラーとし、JSONを上書きしない。
- 編集用JSONはユーザーの設定ディレクトリに保存できる。Daemonのシステムへの反映は必要な権限を取得して行い、JSONの編集だけではrootで実行する設定が変更されないようにする。認証・反映・未反映状態の詳細はDaemon対応時に定める。

## 3. 操作・状態・GUI

### 基本操作

| 操作 | 動作 |
|---|---|
| 有効化／Enable | JSONからplistを生成し、`bootstrap`する |
| 無効化／Disable | `bootout`で終了・登録解除し、plistを削除する。定義とログは残す |
| 再実行／Restart | `kickstart -k`で、待機中なら起動、実行中なら再起動する |

- `stop`の事前実行や、launchctlの`enable`／`disable`による別の管理状態は設けない。
- 有効なサービスは次回ログイン時にも読み込まれ、実行するかはRunAtLoad／KeepAliveに従う。
- 再実行は有効で読み込み済みのサービスに提供する。「今すぐ実行」は設けない。
- 無効化は登録解除を確認してからplistを削除する。
- 操作失敗時は成功扱いせず、実際の状態と再試行可能な操作を表示する。
- 有効化の`bootstrap`失敗時はlaunchdの読み込み状態を再確認する。既に読み込まれている場合は、同時に成功した別の操作による登録を保護するため、後片付けの`bootout`とplist削除を行わず、操作の失敗を返す。終了コードだけで既に有効かどうかを判定しない。状態の再確認に失敗した場合も、誤ってサービスを停止しないよう後片付けを控え、失敗を表示する。
- 初期版ではlaunchd操作全体に対するGUI／CLI間のプロセス間排他は導入せず、上記の有効化失敗時の保護を行う。JSON保存の`flock`は維持し、有効化と無効化など異なる操作の同時実行まで保証するものではない。

内部状態では有効／無効と、待機中／実行中（PID）を分離する。GUIの一覧・メニューバー・詳細画面ではこれらを1つの状態表示にまとめ、「実行中」「待機中」「無効」「要確認」「エラー」のいずれかを表示する。丸ランプは実行中を緑、待機中を黄、無効をグレー、要確認とエラーを赤とする。状態をまだ取得していない間は丸ランプや「不明」を表示せず、読み込み中のインジケーターを表示する。

plistとlaunchdが一致しない場合は「要確認」、launchctlから状態を取得できない場合は「エラー」とする。PIDは詳細画面の独立した項目にだけ表示し、一覧や状態ラベルには含めない。PIDは識別子として桁区切りなしの数値文字列で表示し、コピーする数値文字列と一致させる。前回の終了コード・シグナルは詳細画面に併記する。

詳細画面のステータスカードは、実行中を薄い緑、待機中を薄い黄、要確認・エラーを薄い赤の背景とし、枠線も同系色にする。無効・読み込み中は中立色の背景と枠線を使う。ダークモードでは背景の着色をさらに控えめにし、状態名と丸ランプも併用して色だけに頼らず判別できるようにする。

詳細画面のステータス以下は「識別情報」（Label）、「実行設定」（ProgramArguments・WorkingDirectory・EnvironmentVariables）、「動作」（RunAtLoad・KeepAlive・ThrottleInterval）、「ログ」（StandardOutPath・StandardErrorPath）の4セクションに分ける。項目ラベルは正確なplistキー名のまま翻訳せず、見出しと操作ボタンは日英に対応する。ラベルと値は左揃え・上揃えの2列とし、ラベル列の幅をセクション内の最長ラベルに合わせ、値の開始位置を揃える。値は等幅フォントで選択コピー可能にし、長い値は折り返す。Booleanはtrue／false、ThrottleIntervalは秒数の整数で表示する。未指定のWorkingDirectory・ThrottleInterval、空のEnvironmentVariablesは省略し、環境変数は名前順にKEY=valueを改行表示する。複数項目があるセクションは、表示する項目間をカード幅のDividerで区切り、先頭・末尾には線を置かない。ログの「開く」「Finderに表示」は各パスの下の右端に配置する。

ProgramArgumentsは実行ファイルを含む配列全体を、1引数ずつ「空白＋バックスラッシュ＋改行」で連結し、最終行には連結記号を付けない。空文字は''、空白・引用符・シェル特殊文字を含む値はシングルクォートと適切なエスケープで元の引数を保つ。「コピー」で表示用の文字列そのものをコピーし、画面上の自動折り返しは含めない。コピー対象は実行ファイルと引数だけとし、WorkingDirectory・EnvironmentVariablesは組み込まない。表示・コピーのための引用であり、保存値やlaunchdへの渡し方は変えない。

Label・ProgramArguments・WorkingDirectory・EnvironmentVariables・StandardOutPath・StandardErrorPathは、値の1行目右端にコピーアイコンを常時表示する。複数行の場合も項目全体をコピーする。実行中のPIDにも数値のすぐ右にコピーアイコンを置き、ラベルや桁区切りを含まない数値だけをコピーする。アイコンのツールチップ・アクセシビリティラベルは「〇〇をコピー」を日英で表示する。成功時は押したボタンの上に「コピーしました」／「Copied!」を1.5秒表示し、アイコンをコピーアイコンと同じ控えめな色のチェックマークに切り替える。マウスを離しても時間内は表示し、レイアウト・クリック・フォーカスを妨げない。表示・非表示は控えめなフェードと拡縮、アイコンの切り替えはシンボルの置換アニメーションを使い、「視差効果を減らす」が有効な場合は動きを省略する。通常のツールチップは成功表示中は出さない。連続コピーは最新の項目だけに表示し、古い結果・タイマーが新しい表示を上書き・消去しないようにする。成功時の画面下の通知は廃止し、失敗時だけ詳細ペイン下部に失敗通知を表示する。値そのものは通知に含めず、選択サービスの変更や詳細画面を閉じたときは通知を消す。

### 引数・環境変数の一覧編集

- SwiftUIのTableを使用し、引数は1列、環境変数は名前／値の2列とする。列見出し・空状態・下部の＋／−を備え、セル内の重複ラベルやドラッグハンドルは表示しない。
- 未選択の行は単一クリックで選択し、選択中の行のセルをクリックするか、行選択中にReturnを押すと編集を始める。セルは常にTextFieldとして構築してフォーカスを安定させ、未選択行ではhit testingを無効にしてTableへクリックを渡す。引数の追加は選択行の直後（未選択なら末尾）、環境変数の追加は末尾とし、新しい行へフォーカス・スクロールする。編集画面を開いただけでは行を選択・編集しない。
- 削除後は次の行、なければ前の行を選択する。未選択時は削除できない。
- 引数だけをTableの行全体のドラッグ＆ドロップまたは上下ボタンで並べ替え、順番を保存する。移動後も行の選択を維持する。
- 環境変数は編集画面を開いた時点で名前順に表示し、入力中は自動整列しない。表示順は保存しない。
- Tab／Shift-Tabで入力欄と操作ボタンを移動する。行選択中のDeleteは行削除、文字編集中のDeleteは文字削除とする。
- 一覧は行数に応じて全行が表示される高さに広げ、編集画面全体でスクロールする。保存中は編集・選択・追加・削除・移動を無効にする。
- 1行が1引数であり、空文字・空白・引用符・`$PORT`を含め入力どおりに渡す。Moy独自の変数展開やシェルスクリプト入力機能は設けない。

### 登録・編集・削除

編集画面も「識別情報」「実行設定」「動作」「ログ」の順に構成する。識別情報にはLabel（固定の接頭辞＋Identifier入力欄）・表示名・説明、実行設定にはProgramArguments（実行ファイル・引数）・WorkingDirectory・EnvironmentVariablesを配置する。plist項目のラベルは詳細画面と同じ正確なキー名を使用し、メタデータや実行ファイル・引数の入力ラベルは日英に対応する。項目ラベルの文字サイズを揃え、単一行の入力欄には枠を付け、説明の複数行入力欄にも背景と枠を付ける。WorkingDirectory・ログ保存先はラベルの下に入力欄と選択ボタンを並べる2行表示とする。ProgramArguments内の実行ファイルと引数は字下げせず、実行ファイルだけはラベル・入力欄・選択ボタンを横一列に配置する。実行ファイルのラベルは引数の列見出しに合わせた控えめなサイズとし、入力欄は右端の選択ボタンまで残りの幅を使う。動作のスイッチと秒数入力欄は右端に配置し、ラベルと注意書きを含む項目全体に対して垂直方向の中央に揃える。各項目の上下には共通の4ptの追加余白を設ける。項目固有の注意書きは対象の入力欄と同じ行の中にまとめ、入力欄と注意書きの間にDividerを置かない。LabelとIdentifierは1項目にまとめ、上段の左側にLabel、右側に固定の接頭辞とIdentifier入力欄を並べ、最初のテキストベースラインを揃える。説明は下段で項目全体の幅を使う。説明にはMoy内で一意の識別子として使用すること、入力形式、作成後は変更できないことを記載する。一意の識別子として使用する旨の文の後に明示的な改行を入れ、入力形式と変更不可の説明を次の行にまとめる。有効なサービスの保存時の再読み込みに関する説明は、最後のセクションの背景外にフッターの注釈として表示する。新規作成時のログ入力欄にはMoyKitの共通パス生成を使った既定パスをプレースホルダーで表示し、Identifierの入力に合わせて更新する。未入力・不正なIdentifierの場合はパス内の識別子を<Identifier>で示す。入力値は空欄のまま維持し、保存時に既定パスを確定する。ログの2項目に共通する注釈「空欄の場合は表示されている既定パスを使用します。」は独立した行に置き、その上にセクションのDividerを表示する。

- GUIの新規登録は「保存」のみを用意し、「保存して有効化」は提供しない。保存ではplistを作成しない。成功時は編集画面を閉じ、登録したサービスを選択して詳細画面を表示する。有効化は詳細画面から別の操作として行う。インポート・複製でも同じ流れを使用する。
- 登録・編集の入力検証や保存に失敗した場合は、編集シート自身でエラーを表示する。入力内容を維持して修正・再保存できるようにし、実行ファイルの指定・存在・実行可否のエラーは日英で案内する。編集シートが開いている間は親画面・メニューバーから同じエラーを表示しない。シートを閉じたとき・次の編集開始時・再保存時は以前のエラーを消す。
- 無効なサービスの編集はJSON保存のみ。
- 有効なサービスのlaunchd設定変更はJSON保存後に再読み込みする。実行中だった場合は再実行し、待機中だった場合は実行条件に委ねる。保存ボタンのラベルは「保存」のままとし、保存後に反映の確認ダイアログは表示しない。
- JSON保存後にlaunchdへの設定反映が失敗した場合は、新しい定義をJSONに残し、旧定義・plist・管理状態への復元は行わない。保存成功と反映失敗を通常の保存失敗と区別してGUI／CLIに伝える。GUIでは保存済みの編集シートを閉じて一覧と状態を再取得し、管理画面で反映失敗を通知して、手動の無効化・再有効化を行えるようにする。CLIでは保存済みであることと反映失敗を英語で表示し、非ゼロの終了コードを返す。GUIでは「設定は保存しましたが、サービスへの反映に失敗しました。サービスの状態を確認し、有効な場合は一度無効化してから、再度有効化してください。」に相当する日英のエラーを表示し、具体的な失敗理由も併記する。新しい設定を反映するため、無効な場合は有効化し、有効な場合やplistとlaunchdの状態が一致しない場合は無効化してから再度有効化できるようにする。再起動は読み込み済みの設定で再実行する操作であり、JSONの新しい設定を反映する操作ではない。
- 削除は確認後に無効化し、JSONからも削除する。ログは残す。

### 画面と状態管理

- メニューバーには登録済みサービスを全件表示し、一覧領域に最大高を設けて、収まらない場合はスクロールできるようにする。メニュー表示時、および件数が増えてスクロールが必要になったときにスクロールインジケーターを点滅させ、続きがあることを示す。
- メニューバーの一覧は5秒ごとにバックグラウンドで更新する。ヘッダーには更新中のアクティビティインジケーターを表示せず、初回の読み込み表示と取得失敗時のエラー表示で状態を伝える。
- メニューバーと管理ウィンドウのサイドバーの更新ボタンは共通のコンポーネントを使用し、押したボタンのアイコンを時計回りに一度回転させて操作への反応を示す。定期更新では回転させず、macOSの「視差効果を減らす」が有効な場合は回転アニメーションを省略する。ツールチップとアクセシビリティラベルも共通化し、ボタンのスタイルと無効化条件は配置側で指定する。
- メニューバーの各サービスは、状態の丸ランプ・表示名と、右端の薄い円形背景を持つ「…」アクションボタンだけの簡潔な行として表示する。アクションメニューに有効化／無効化、再実行、標準出力・標準エラーログの操作、および「詳細」を配置する。「詳細」は管理ウィンドウを開き、対象サービスを選択した状態で詳細画面を表示する。
- サービスのサブメニューは「詳細」、区切り線、基本操作、区切り線、「ログ」の小見出しの順に配置する。ログは「標準出力」「標準エラー」をそれぞれサブメニューにし、各サブメニューに「開く」「Finderに表示」を配置する。
- 管理ウィンドウで一覧・詳細・登録・編集・削除を提供する。
- 管理ウィンドウの左ペイン下部に、サービス一覧を更新するボタンを左端、サービスを追加するボタンを右端として固定配置する。
- 管理ウィンドウ右上のツールバーに歯車を常時表示し、選択中サービスに対する編集・削除とは別のグループとして配置する。歯車は独立した設定ウィンドウを開く。メニューバーの「サービスを管理」と「終了」の間にも「設定…」を配置する。どちらからも同じ単一ウィンドウを開き、開いていれば前面に表示する。
- 管理ウィンドウの右ペインに汎用の「サービス」タイトルは表示せず、選択中のサービス名を詳細のタイトルとして表示する。
- 詳細画面は右ペインの横幅を使い、サービス名の下にコピー可能なIdentifier、設定されていればdescriptionを表示する。ステータスカードは左側に状態・実行中のPID・前回の終了コードを横一列に並べ、右側に有効化／無効化・再起動ボタンを配置する。ボタンは角丸矩形で、アイコンなしの文字だけを表示する。背景はライト／ダークモードに応じた不透明な中立色のグレーとし、カードの状態色が透けないようにする。押下時は背景の明度を変え、操作不可のときは文字を薄く表示する。横幅が不足する場合は操作ボタンを下段の右端に配置し、ステータス項目も収まらなければ縦に並べる。Launchd Labelは識別情報セクションで確認・コピーできる。
- 設定ウィンドウはMiroCalと同様の「設定」「情報」の2タブとする。「設定」にCLIの説明・インストール操作・状態・インストール先・PATH設定の案内をまとめる。「情報」にアプリ名・バージョン・ビルド番号を表示し、専用アイコンがない間はターミナルのシンボルを使う。アプリアイコンは見えている本体が120pt角になるよう標準の周囲余白を補正し、本体の下辺とリンクの下辺を揃える。情報欄との間隔は16pt、アプリ名は24ptの太字とする。上部のタブ領域を考慮して中央の内容を24pt上に補正し、ウィンドウ全体の縦方向中央に配置する。ウィンドウ下部に「Copyright © 2026 Yoshihiro Kato. All rights reserved.」を控えめに表示し、中央の配置に影響させない。バージョンの下にGitHubアイコンと「Repo」のリンクを配置し、`https://github.com/yshrkt/Moy`を開く。ツールチップとアクセシビリティラベルは日英で「GitHubリポジトリを開く」に相当する説明を用意する。お問い合わせ・プライバシーポリシーはまだ配置しない。
- 設定ウィンドウの上部バーとコンテンツには同じ不透明なwindowBackgroundColorを使用し、ライト／ダークの両表示で背景色を揃える。上部バーの背景は常時表示し、ブラーを使用せずスクロール内容がタブやウィンドウ操作ボタンと重なって見えるのを防ぐ。設定Form固有のスクロール背景と上端のスクロールエッジ効果は非表示にする。「設定」「情報」の切り替えはTabView（tabBarOnly）で行う。
- 設定タブの説明・注意文は`.callout`と`.secondary`で統一し、コマンド・パスは同サイズの等幅フォントとする。項目名・操作ボタンは通常サイズを維持する。CLIの冒頭の機能説明と認証説明は改行を含む1つの日英文字列・Textで表示し、通常の行間を使う。CLIとターミナル設定の項目間隔は12pt、追加の上下余白は6ptに統一する。情報タブの文字サイズは変更しない。
- 設定の先頭に「一般」セクションと「ログイン時に起動する」スイッチを配置する。MiroCalと同じ`SMAppService.mainApp`でMoy本体を登録・解除し、未登録時はOFFとする。起動時に自動登録しない。ログイン時はメニューバーだけに起動し、管理・設定ウィンドウは開かない。
- ログイン項目の状態はmacOSを正本とし、独自のBooleanを永続化しない。設定を開いたとき・再びアクティブになったときに取得し、取得・更新中はスイッチ操作を無効にする。登録後・解除後・失敗後にも実際の状態を取得する。承認待ちは登録済みとしてスイッチをONにし、起動可能な状態と区別して承認の説明とシステム設定のログイン項目を開くボタンを表示する。未登録・項目不在の状態では注意文を表示せず、スイッチと通常の説明だけを表示する。変更失敗は設定ウィンドウ内の日英エラーにOSの理由を併記する。
- ログイン時起動のUseCaseはMoyKitのDomain／Platformに分離し、SettingsのEffectから呼び出す。Moy自身のログイン項目はサービス定義のJSON・plist・一覧に含めず、登録サービスのRunAtLoad／KeepAliveやサービス操作には影響させない。
- 設定機能のAction／State／Reducer／DependenciesはServicesから分離し、アプリでSettingsのStoreを保持する。設定内のエラーは設定ウィンドウで表示する。
- 標準出力・標準エラーに「開く」「Finderで表示」を提供する。
- Moyを終了しても、launchdによるサービス管理は継続する。

メニューバーと管理ウィンドウでStoreを共有し、機能ごとにscopeする。一覧、選択、処理中状態、エラーをAction／Reducerで管理する。編集機能は`Core/ServiceEditor`のAction／State／Reducer／Dependenciesに分離し、Servicesの子機能として合成する。編集画面にはscopeしたStoreを渡し、入力内容・行選択・ファイル選択・入力検証・保存中状態・編集エラーは子機能が管理する。Servicesは編集の開始・終了と保存Effectを担当し、子から保存用payloadを受け取り、保存結果を子へ返す。成功時は編集画面を閉じて一覧を更新し、失敗時は入力を維持する。編集セッションのIDを照合し、古い非同期結果を次の編集へ反映しない。保存・launchd操作・状態更新はEffectから依存注入したUseCaseを呼び出し、操作の重複実行を防ぐ。説明の複数行入力欄は即時更新するView内の入力状態にバインドし、変更内容をAction経由で編集状態に反映する。非同期のStore更新によって入力途中の古い文字列を読み戻さず、かな漢字変換と途中位置での追記時もカーソル位置を維持する。

## 4. ローカライズと同梱CLI

### GUIの日本語・英語対応

- MiroCal同様、`Localizable.strings`とTuistの文字列生成を利用し、`L10n`経由で参照する。
- メニュー、フォーム、説明、状態、確認ダイアログ、エラー、アクセシビリティラベルを日英で用意する。
- macOSの優先言語に従い、未対応言語では英語にフォールバックする。
- ユーザー入力の表示名・descriptionは翻訳しない。
- 文字列変更時は`mise run generate`を実行する。開発ドキュメントは日本語を基本とする。
- MoyKitは型付きエラーを返し、MoyAppで日英の表示メッセージに変換する。
- Moyが定義する入力検証理由は文字列ではなく型付きの列挙型で返し、GUIでは全ケースを日英に変換し、CLIでは英語で表示する。OSやlaunchctl由来の詳細は、日英の説明に原文を併記する。

### CLI

CLIは**ヘルプ・メッセージとも英語のみ**とし、ローカライズ用リソースbundleは使用しない。

| 分類 | コマンド |
|---|---|
| 定義管理 | `add`、`edit`、`remove`、`list`、`show`、`import`、`export` |
| 操作 | `enable`、`disable`、`restart` |
| 状態・ログ | `status`、`logs` |

- CLIではIdentifierでサービスを識別し、新規登録時に`--identifier`で指定する。
- 同じ9項目、表示名、descriptionを扱い、MoyKitのUseCase／Repositoryを共通利用する。
- 一覧・詳細・状態の`--json`出力、ヘルプ、明確な終了コードを提供する。
- MoyKitのエラーをCLI側で英語メッセージに変換する。
- コマンド名、オプション、JSONキー・状態値、plistキーはロケールに依存させない。
- 設定ウィンドウから`/usr/local/bin/moy`へのリンクを作成する。通常ユーザーで書き込めない場合のみ、macOS標準の管理者認証を経てディレクトリ・リンクを作成する。Moy本体とサービス操作は通常ユーザー権限のままとする。
- 管理者認証はMoyプロセス内で`NSAppleScript`を使って要求し、外部の`osascript`は起動しない。メインスレッドでスクリプトのハンドラーを呼び出し、コマンドはApple eventの引数として渡す。認証元がMoyとして表示されることは実機で確認する。
- 管理者認証の終了後は、成功・キャンセル・エラーのいずれでも、認証前の設定ウィンドウを前面に戻してフォーカスを復帰する。通常の状態取得・更新では前面化しない。
- 認証をキャンセルした場合はエラーを表示せずインストール前の表示へ戻り、実際の状態を再確認する。認証の失敗・リンク作成の失敗はエラーとして表示し、インストール後のリンクを確認できるまで成功扱いしない。
- 既存ファイル・リンクは認証後にも確認し、上書きしない。以前の`~/.local/bin/moy`は自動削除・移行しない。
- `/usr/local/bin`は通常PATHに含まれるため、設定では`moy --help`による確認を案内し、見つからない場合にPATHの確認を促す。
- 設定を開いたとき・再びアクティブになったときにリンクを確認し、アプリ再起動後もインストール済み状態を実体から判定する。メニューバーアプリではSwiftUIのscenePhaseだけで復帰を検知できない場合があるため、AppKitのアプリ再アクティブ化通知でも確認する。「Finderに表示」から対象を削除して設定画面へ戻った場合にも実際の状態を反映する。未インストール時は「インストール」、現在の同梱CLIを指す有効なシンボリックリンクがある場合は「インストール済み」と「アンインストール…」を表示する。確認中・インストール中・アンインストール中は重複操作を防ぐ。
- アンインストールは確認ダイアログを経て`/usr/local/bin/moy`のリンクだけを削除する。リンク先の同梱CLI、登録済みサービス、設定・ログは残すことを説明する。通常ユーザーで削除できない場合のみ、インストールと同じ方式で管理者認証を要求する。キャンセル時はエラーを表示せず実際の状態を再確認する。削除後の状態を確認できるまで成功扱いしない。
- 削除直前（管理者認証が必要な場合は認証後にも）に、現在の同梱CLIへの有効なリンクであることを再確認する。確認後にリンクが変更・削除された場合は削除を中止し、エラーダイアログを表示して状態を更新する。専用の再確認フローは設けない。
- 別のリンク先・リンク切れ・通常ファイル・ディレクトリは競合として表示し、インストール・アンインストール・上書きは提供しない。競合の説明と「Finderに表示」を提供し、ユーザー自身で対処してもらう。文言は既存の`L10n.Common.reveal`（日本語「Finderに表示」、英語「Show in Finder」）を共用する。Finderではリンク先ではなく`/usr/local/bin/moy`自体を選択して表示する。アプリ移動によるリンク切れもこの扱いとする。

## 5. 検証と完成条件

- **個別JSON・複製・入力中検証**：全設定の入出力と任意項目の省略、既定／独自ログパスの引き継ぎ、入力中のIdentifier形式・一覧内重複の検出とファイル／launchctlアクセスを行わないこと、保存時の厳密な重複検査、形式不正時とキャンセル時に登録されないこと、保存時の実行ファイル検証、CLIの上書きと書き込み失敗、--enableの有無、GUIが保存のみで詳細を表示すること、日英表示。
- **識別子・保存**：Identifierの形式・一意性・不変性、同時登録、Label算出、9項目とメタデータの保存・復元、JSON破損・競合・未対応バージョン。
- **実行**：スペース・空文字・引用符を含む引数、環境変数、作業ディレクトリ、指定ログ出力先。
- **ライフサイクル**：RunAtLoad／KeepAliveの組み合わせ、待機中・実行中の再実行、KeepAlive有効時の無効化。設定反映失敗時に新しい定義がJSONに残り、旧状態への復元を行わず、保存成功・反映失敗と状態確認の案内を表示すること。同時有効化の片方が成功して他方の`bootstrap`が失敗した場合に、成功した登録とplistが後片付けで撤去されないこと。有効化失敗後の状態確認が失敗した場合にも、`bootout`とplist削除を行わないこと。
- **状態管理**：NanoReduxのReducer／Effect、CLI変更の反映、メタデータ変更でプロセスを再起動しないこと。
- **ローカライズ・CLI**：日英のキーと書式引数の一致、英語表示でのレイアウト、CLIがロケールによらず英語になること、JSON出力の安定性、リンク経由のCLI実行、管理者認証の成功・キャンセル・失敗、既存ファイルの保護、空白・引用符・シェル特殊文字を含むアプリの配置パス。
- **CLIのアンインストール・競合**：インストール済みの場合のみアンインストールを提供すること、確認・認証のキャンセル、削除失敗、削除直前のリンク変更時のエラーと状態更新、削除後の状態確認。リンク先・サービス・設定・ログが残ること。別リンク・リンク切れ・通常ファイル・ディレクトリでは削除を提供せず、既存と同じ文言でFinderに対象自体を表示すること。
- **ログイン時起動**：未登録・有効・承認待ち・項目不在（未登録・項目不在では注意文を表示しない）、登録・解除・失敗後の実状態取得、重複操作防止、システム設定から戻った際の再取得、日英の表示。実機では設定のON／OFF、ログアウト・ログイン後のメニューバー起動とウィンドウ非表示を確認する。
- **実機・ビルド**：専用テストジョブでPID・終了結果・ログを確認し、登録を撤去する。アプリと同梱CLIのDebug／Releaseビルド、format／lintを確認する。
- **ドキュメント**：READMEはアプリ全体の概要・動作環境・ビルド方法・基本操作を中心とし、機能の一覧は短い説明にとどめる。個別機能の詳細な手順・ファイル形式・CLI仕様・開発手順は必要に応じてdocs配下の別ドキュメントに記載する。JSONインポート・エクスポートの詳細セクションはREADMEに設けず、仕様は本プランに集約する。

初期版の完成条件は、日英対応GUIと英語CLIをローカルでビルド・利用できること。既存plistの取り込み、システムDaemon、定期実行・監視設定、ログビューアー・ローテーション、配布・自動更新は次段階とする。

### 公開に向けた配布方針

ZIPまたはDMG形式でのバイナリ配布を検討する。形式と配布手順は未確定とし、未確定の配布予定はREADMEに記載しない。署名・公証・パッケージ作成の実装は別途行う。

公証に向けて、MoyAppと同梱CLIのMoyCLIではHardened Runtimeを有効にする。Tuistの両ターゲットに`ENABLE_HARDENED_RUNTIME = YES`を設定し、App Sandboxは無効のままとする。
